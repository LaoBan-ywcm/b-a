# b-a

Go 实现的 Binance USDT 永续合约上涨提醒服务。启动立即读取公共行情，此后默认每分钟检查，按 24 小时滚动涨幅取前 N 名，用最近一根已收盘周线确认后向 Telegram 私聊发送提醒。同一合约成功通知后默认冷却 10 分钟，重启继续保留冷却。

默认条件：正在交易、USDT 报价和保证金、永续合约；涨幅排名前 10；24 小时涨幅严格大于 100%；已收盘周线涨幅大于等于 20%。并列按合约标识排序；排除列表在排名截取后应用，不递补后续合约，不设置成交额门槛。

## 构建与运行

需要 Go 1.25 或更新版本，无第三方依赖。

```sh
go build -o /tmp/binance-monitor ./cmd/binance-monitor
```

在运行环境中提供 `TELEGRAM_BOT_TOKEN` 和 `TELEGRAM_CHAT_ID`，接收者需先与 Bot 建立私聊。`TELEGRAM_CHAT_ID` 使用正整数私聊 ID。凭证不要写入仓库或命令参数；由服务器环境或秘密管理工具注入。本项目不需要 Binance API Key 或交易权限。

```sh
# 目录由程序创建；运行账户需有父目录创建权限，并独占该状态文件。
STATE_PATH=/var/lib/binance-monitor/cooldowns.json /tmp/binance-monitor
```

程序持续运行，以 `SIGINT`（终端 Ctrl-C）或 `SIGTERM` 正常停止，退出码为 `0`。启动后无需积累行情历史；每轮刷新合约范围与排名。检查串行执行，按本轮开始时间计算下一周期，慢轮次错过的检查时刻直接跳过，不重叠，也不补跑中断期间的旧行情。

无符合条件合约属于正常结果。API 请求失败会记录日志并继续下一周期；部分候选请求失败时，其他数据完整的候选仍可发送。配置非法、状态损坏或状态写入失败会停止服务，退出码为 `1`。标准输出提供启动提示，标准错误提供轮次摘要和诊断，不输出 Telegram Token、原始请求 URL 或远端错误正文。

采用单进程、单实例部署：同一状态文件只允许一个进程写入，目前不提供多实例锁或协调。可由已有进程管理器运行上述命令；本仓库不自动配置服务、凭证或生产部署。

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | 必填 | Telegram Bot Token |
| `TELEGRAM_CHAT_ID` | 必填 | 私聊 ID |
| `TOP_N` | `10` | 排行榜数量，正整数 |
| `DAILY_THRESHOLD_PCT` | `100` | 24 小时涨幅门槛，严格大于 |
| `WEEKLY_THRESHOLD_PCT` | `20` | 已收盘周线涨幅门槛，大于等于 |
| `EXCLUDED_SYMBOLS` | 空 | 逗号分隔的合约，如 `BTCUSDT,ETHUSDT` |
| `CHECK_INTERVAL` | `1m` | 检查周期，必须为正；例如 `30s`、`2m` |
| `COOLDOWN` | `10m` | 每个合约成功通知后的冷却时长，必须为正 |
| `STATE_PATH` | `data/cooldowns.json` | 本地持久状态文件；相对路径相对于启动工作目录 |
| `HTTP_TIMEOUT` | `10s` | 每个 HTTP 请求的超时，必须为正 |
| `BINANCE_BASE_URL` | `https://fapi.binance.com` | 公共行情地址，可用于本地模拟服务 |
| `TELEGRAM_BASE_URL` | `https://api.telegram.org` | Telegram API 地址，可用于本地模拟服务 |

阈值使用非负十进制文本并进行精确有理数比较；通知中的周线涨幅最多保留 12 位小数，展示舍入不会改变筛选结果。周线是否结束以 Binance `/fapi/v1/time` 为准，检查时间使用本地时钟并附带时区，调度和冷却使用本地时间。通知中的参考起点价与最新成交价来自同一份 24 小时 ticker。

缺少已收盘周线属于正常跳过；价格缺失、无效、非正属于无法确认的行情故障，跳过相关合约并输出诊断。程序不会用尚未收盘的本周涨幅，也不会回退到较旧但有效的周线替代价格损坏的最新已收盘周线。

## Telegram 合并与可靠投递

同轮达标且不在冷却期的合约按涨幅排名合并为纯文本，立即发送，不增加主动合并等待（0 秒，低于 3 秒预算）。每条消息保留完整合约块，并按保守的 UTF-16 编码单元计数限制在 4096 以内，中文和 emoji 不会被截断。单个异常合约块本身超过限制时明确报错，不发送截断结果。同一私聊所有发送和重试共用每秒最多一条的速率入口。

临时 HTTP 错误（408、429、5xx）、传输失败、超时或无法解码的响应最多尝试 3 次，退避为 1 秒、2 秒；永久拒绝直接结束。429 的 `parameters.retry_after`（以及存在时的 `Retry-After` 秒数头）会延长等待，即使最后一次重试耗尽，禁发时刻也跨检查轮次保留。限流与重试等待独立于主动合并预算。

上涨提醒有效期从本轮检查开始计算，取 `CHECK_INTERVAL` 与 1 分钟中较短者，行情获取耗时也计入；等待后超过有效期、下一允许发送时刻超出有效期时放弃当前批次。每轮重新读取和筛选当前行情，不积压历史通知。限速闸门保留在单实例内存，重启后不保留服务端限速时刻；冷却状态则持久保存。

## 行情容错与故障恢复

Binance 的公开请求设有 `HTTP_TIMEOUT`；网络错误、读取中断、408、5xx 最多尝试 3 次，通常等待 1 秒和 2 秒。永久 4xx、无法解析的完整 JSON 和无效业务字段不会盲目重试。429 / 418 立刻停止继续请求，保留全实例共享的禁发时刻；有 `Retry-After` 时遵守秒数或 HTTP 日期，缺失时首次 429 等待 1 分钟、418 等待 2 分钟，连续限流倍增，最大 24 小时。408 / 5xx 携带 `Retry-After` 时也使用该闸门。闸门约束后续候选和后续轮次，期满由下一次正常检查重取快照。

候选周线采集共用当前上涨提醒剩余有效期的一半，并按尚未检查的候选均分剩余预算；实际请求超时取 `HTTP_TIMEOUT` 与当前候选份额中较短者，退避也受该份额约束。慢候选不能耗尽后续健康候选的请求与投递机会。预算不足或超时记为局部行情失败，下一轮重新检查；完整结果按原排名立即合并，不额外等待。

行情故障分为全局和局部：无法确认合约范围、排名、交易所时间或遇共享限流时，通知明确标记全局影响；个别合约价格或周线无法检查时，通知标记对应局部合约，其余完整候选继续监控。全局失败期间无法证明局部范围已恢复，因此不会误报局部恢复。某合约退出候选或不再交易时，会说明其已正常或不再需要检查，不声称已经取得该合约周线。

故障从首次失败检查完成时开始计时，连续不可检查**严格超过 1 分钟**，在下一次检查结束时发送一次故障提醒；同一事件持续失败不会重复刷屏。默认每分钟检查时，恰好满 1 分钟不通知，通常在第三个连续失败轮次报告。首次恢复检查发送一次恢复提醒；短暂故障、正常无信号和没有已收盘周线都不会触发故障通知。健康提醒与上涨提醒共用 Telegram 每秒最多一条的闸门，但不写入或延长上涨提醒冷却。

Telegram 真正尝试投递且最终失败时，日志记录“Telegram 通知中断”，保留起点和失败次数。消息过长、行情已过期但尚未发出请求、用户停止服务不冒充 Telegram 中断。即使没有新的上涨信号，后续检查也会尝试发送恢复汇报；只有确认汇报送达才记录“Telegram 通知恢复”。本轮上涨投递已失败时，不再递归发送健康消息；每次投递仍最多尝试 3 次，并遵守服务端限流。健康汇报每次最多等待 1 分钟有效期，不建立旧消息队列。

恢复汇报会合并当前故障与此前恢复事件；已恢复但汇报延迟的旧事件明确标记为“此前事件”，并说明当前是否仍有故障。每类摘要最多展示 6 个范围，过长合约标识截短，另外报告省略数量；完整失败诊断保留在日志。总消息保持在 4096 UTF-16 编码单元以内。若故障提醒从未成功送达且行情已恢复，不补发已过时故障；通知链路恢复仍汇报中断。中断期间的上涨提醒不保存、不补发，恢复后只判断新快照。

健康事件、待汇报摘要和 Binance / Telegram 禁发时刻存在实例内存，进程重启后重新观察；仅上涨冷却持久保存。API 长时间限流时不要用反复重启绕过等待。服务器仍应由现有进程管理器或外部监测检查进程存活：进程停止、主机失联或持久化致命错误时，本程序无法自行发出健康通知。

## 持久化与故障排查

只有 HTTP 成功且 Telegram 明确返回 `ok=true` 才启动该合约冷却，从成功确认后的本地时间计时。不同合约独立计算，到期仍达标可以再次提醒。通知失败不会消耗冷却，不排队重放旧行情；下一轮重新检查当前条件。

每个拆分批次确认成功后，立即为该批次内全部合约保存状态；后续批次失败不会影响已成功批次，也不会提前冷却失败合约。保存方式：同目录写入 `cooldowns.json.tmp`、同步文件、原子重命名替换正式文件、同步目录。新目录权限为 `0700`，新状态文件为 `0600`。服务器或容器重建时应保留整个状态目录，使用支持原子重命名和文件/目录同步的本地持久文件系统。不要把运行状态放入 Git 或随发布替换的临时目录。仓库 `.gitignore` 已忽略默认 `data/` 状态目录、根目录 `binance-monitor` 和 `bin/` 构建目录；自定义路径需放在仓库外。

正式状态文件缺失时按首次启动处理；文件存在但内容损坏、版本不支持、读取失败时拒绝启动，不静默清空。残留 `.tmp` 不用于恢复，也不会覆盖启动时读取的正式状态。保存失败会立即停止后续发送，上一份正式文件保持完整；检查运行账户权限、磁盘空间和文件系统支持，修复后重启。不要随意移除状态文件，否则已发通知的冷却信息会丢失。

Telegram 发送和本地写入无法构成跨服务事务；网络响应结果不明、发送后到保存前崩溃等情况仍可能产生重复提醒，不保证严格一次性发送。

重启或升级时，先通过进程管理器停止旧实例（发送 `SIGTERM` 并等待退出），保留原 `STATE_PATH` 指向的正式状态文件，再用相同运行账户、工作目录和环境启动新二进制。需要备份时在停止实例后备份整个状态目录；不要让新旧二进制同时写入。主机本地时间应保持准确，避免时钟大幅跳变影响冷却和故障持续时间。

| 现象 | 检查方向 |
| --- | --- |
| 长期没有上涨提醒，但轮次正常 | 默认日涨幅门槛很高；检查排行榜、排除列表、已收盘周线及冷却期，正常无信号不算故障 |
| 全局行情故障 | 检查出站网络、DNS、Binance 地址和状态码；429 / 418 等待禁发期结束，不反复重启 |
| 局部合约故障 | 日志定位合约，检查 ticker 价格和周线数据；其他合约仍继续运行 |
| Telegram 通知中断 | 检查出站网络、运行环境注入的 Token、正整数私聊 ID、用户是否先与 Bot 私聊以及限流；日志不展示 Token |
| 冷却状态解析或读取失败 | 检查正式文件版本、完整性和权限；从可信备份恢复，不直接清空状态 |
| 冷却状态写入失败、程序退出 | 检查目录归属、空间和原子重命名/同步支持；修复后保留同一状态文件重启 |
| 没有任何轮次日志 | 检查进程管理器状态、退出码、标准错误收集和主机网络；程序离线无法自报 |

# 仅访问本机模拟服务，展示完整运行与重启流程。

测试通过本地 `httptest` Binance/Telegram 服务和可控时钟执行完整应用检查，包括筛选边界、连续调度、冷却边界、状态重建、写入失败、全局/局部故障、Telegram 中断恢复与消息长度/速率；测试端点固定在本机，不调用真实账户或发送真实通知。运行环境需要允许监听本机随机端口。若 Go 构建缓存目录不可写，可以添加 `GOCACHE=/tmp/b-a-go-cache`。

## 当前边界

这是行情观察服务，不提供交易、持仓、回测、Web 管理界面或多用户订阅。异常上涨不代表未来仍会上涨。当前约定为单实例部署，不提供分布式协调；通知不承诺严格一次性，健康事件不跨重启保留。
